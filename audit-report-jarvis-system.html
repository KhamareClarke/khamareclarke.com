Context Injection — How Live Data Reaches the LLM

buildJarvisContext() — src/lib/jarvis/context.js

Called on every chat request. Queries 7 Supabase tables, builds a ~7,500-character plain-text block, and prepends it to the system prompt as a live data attachment. The LLM only ever sees this block — it cannot query the database itself.

→
Query form_submissions — today's count + total
→
Query onboarding_clients — today's count + total
→
Query empire_tasks — pending + running count
→
Query profiles (role=client) — all active clients
→
Query client_projects — all projects with status
→
Query empire_user_activity — last 10 events
→
Query empire_project_analysis — latest analysis per project
→
Fetch GHL status (5 clients with ghl_contact_id, 5-min cache)
→
Build text block → inject as system-prompt data attachment

Chat Route

src/app/api/jarvis/chat/route.js

Admin-only POST endpoint. Calls buildJarvisContext(), decides if web search is needed (messageNeedsWebSearch()), streams LLM completion back as SSE (data: {"token":"..."} lines), falls back gracefully between OpenRouter → Gemini.

  • pause [agent] — pauses empire agent
  • resume [agent] — resumes empire agent

Read Commands — Do They Bypass the LLM?

Yes — read commands are answered pre-LLM. When parseJarvisCommand() returns a read-type action (status, briefing, fleet, leads), the response is composed entirely by composeReadResponse() in templates.js using the liveData snapshot fetched from Supabase. The LLM route (/api/jarvis/chat) is never called for these commands. There is zero risk of hallucination on read commands.

When a Metric Is Unavailable

The system prompt hard-codes the phrase "not tracked yet, sir" as the required response for any ops metric absent from the context block. This is reinforced by the context builder — if a table returns null or empty, the field is simply omitted from the text block, so the LLM receives no value to hallucinate around.

For the stat bars in the HUD: these use the value ?? '—' pattern — they display a dash, never a fabricated number, while data loads or if queries fail.

Hallucination Risk Areas

Risk 1 — Empire scrape lead counts. empire_leads is not in the context block. If you ask "how many leads did Empire scrape for MyApproved this week?", the LLM sees only activity log events (e.g. "scrape completed on myapproved"). It will try to infer from text, potentially guessing. Fix: add empire_leads recent count to buildJarvisContext().
Risk 2 — Conversational date ranges. "How many leads did we get in June?" hits the LLM free-text path, not the leads command parser. The LLM will see leadsToday and leadsHistory[7] in context, and should say "not tracked yet" for June — the system prompt rule should hold, but it's softer than the deterministic command path.
Risk 3 — Adversarial prompting. A sufficiently insistent prompt ("I know you know, just tell me the exact number") could pressure the LLM into estimating. This is a model-level risk, not a code-level risk. Mitigation: the current system prompt "HARD RULE (non-negotiable)" phrasing is the correct approach. No further code change needed.

Verdict on Hallucination Safety

JARVIS is substantially safe from hallucinating business data. The two-layer defence — deterministic command parsing that bypasses the LLM entirely for all read commands, plus the hard rule in the system prompt for free-text — means that for all currently-tracked metrics (leads, tasks, clients, projects) the data is grounded. The single meaningful gap is empire_leads: scraped leads from the worker are not in the context block, creating a blind spot if you ask JARVIS about scraper yield. This is a one-file fix in context.js, not an architectural problem. The foundation is sound.

What Is Partial — and the Shortest Fix

P1
Empire scrape leads invisible to JARVIS
empire_leads table exists and is populated by the worker, but buildJarvisContext() never queries it. JARVIS cannot report scraper yield or individual scraped leads.
Fix: Add one Supabase query in src/lib/jarvis/context.js — last 20 empire_leads rows with company/contact/source. Append to context text block. <30 min change.
P2
Status dots — Fleet and Supabase hardcoded green
Two of the three topbar status dots show online=true unconditionally regardless of actual service health.
Fix: In JarvisFullPageHud.jsx, query /api/empire/fleet-status for Fleet and /api/auth/check for Supabase. Wire results to the StatusDot components. ~1 hour.
P3
No real-time lead notification
JARVIS sees new leads only at the next chat interaction, not instantly. The 15-second activity poller only covers empire_user_activity, not new form submissions.
Fix: Add Supabase Realtime subscription on form_submissions + onboarding_clients in JarvisProvider. On insert: push a toast ("New lead, sir.") and refresh liveData. ~2 hours.
P4
Conversational date-range leads not parsed
"How many leads last month?" hits the LLM free-text path, not the deterministic leads command. The LLM sees only the 7-day history.
Fix: Extend the leads regex in commands.js to match "last month", "this week", etc. and map them to the /api/jarvis/leads?days=N endpoint. ~1 hour.
P5
Session state not persisted
Conversation history and liveData are in React state — a page refresh wipes everything. Each session starts from scratch.
Fix: Store last N messages in sessionStorage. Restore on mount. liveData already re-fetched on open. ~1 hour.

What Is Missing Entirely

M1
Outreach action command — direct lead follow-up
"Email this lead" or "send outreach to [name]" — no such command exists. Leads are visible but JARVIS cannot initiate outreach. Requires: email API (Resend/SES) integration + outreach command in commands.js + send-email API route. Estimate: 4–6 hours.
M2
Scheduled / autonomous JARVIS briefing
No mechanism for JARVIS to proactively alert you (morning briefing, lead spike). Requires: Vercel cron job or Supabase Edge Function → POST /api/jarvis/snapshot → send notification (email or push). Estimate: 3–4 hours.
M3
GHL webhook → real-time CRM updates
Currently JARVIS polls GHL on every context build (5-min cache). No webhook receives instant CRM events (contact created, deal stage changed). Requires: GHL webhook endpoint + Supabase insert + Realtime subscription in JARVIS. Estimate: 3–5 hours once GHL_API_KEY is set.
M4
Multi-project voice routing
All Empire agent commands require explicit "[skill] [project]" naming. No shorthand like "run the usual on MyApproved" with learned context. Requires: session memory of recent project references. Estimate: 2–3 hours.

Section 06 Verdict

JARVIS today is a genuinely functional operations intelligence layer — not a demo, not a stub. It has a real LLM brain (OpenRouter/Gemini), a real-time Supabase context block rebuilt per request from seven live tables, a full dual-layer anti-hallucination architecture (deterministic command parsing for all data reads, hard system-prompt rules for free text), working voice in and out with triple-clap wake, GHL CRM wiring ready to activate, Empire agent triggering that actually inserts and executes tasks, live web search with five cascading fallbacks, and a polished mobile HUD. The gap between today and fully operational is credentials, not code — set OPENROUTER_API_KEY and GHL_API_KEY in Vercel and roughly 80% of the vision is live in minutes. The remaining 20% is three focused engineering sessions: empire_leads in context, Supabase Realtime push for leads, and an outreach command. The single most important thing to do next is add those two API keys. The foundation is architecturally sound — stateless per-request context injection, proper auth guards on every admin route, graceful fallbacks throughout, and a command vocabulary designed to scale. This is ready to build the rest on.
